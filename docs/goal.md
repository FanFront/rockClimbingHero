# RockClimbingHero · Codex 下一轮目标
## Phase：The Living Expedition（鲜活的探险世界）

> **只做 Android，默认中文、保留英文。请直接修改项目代码并提交 GitHub，不要只写方案。**
>
> **本轮首要目标：把“攀岩打卡获得数值”变成“现实训练推动一个会回应玩家的像素 RPG 世界”。**
>
> **优先实现乐趣与美术，最小化测试和文档；不要为架构、后端或测试耗掉开发时间。**

### 开发前提
- 仓库已有 React Native + Expo + TypeScript、SQLite 离线存档、日/周随机委托、五维 RPG 成长条、线路图鉴和 Android 原相册媒体引用。**复用现有功能，不重造训练记录器。**
- 保持当前存档和历史数据可读取：旧 `AppData.schema=1`，现有 `sessions / assessments / commissions / questLedger / routes / detailedRouteSessions / demonstrations` 均不能丢。新增世界状态用兼容的可选字段或轻量迁移。
- 仍保留：真实训练结算 XP 与游戏属性成长；原有自评代表真实主观能力，不自动篡改；疼痛/休息保护；离线可用；媒体只保存用户相册 URI，不复制文件。
- **游戏不应鼓励为刷奖励过度攀爬。** 休息/舒展同样可触发冒险，不做连续签到惩罚；新装备仅影响外观、故事或探索，不伪造现实身体素质。

### P0：把营地真正做成一个“活着的游戏场景”
- 首页从普通卡片/静态 SVG 升级为**大幅可交互的高品质像素营地**：篝火、帐篷、角色、NPC、公告板、地图路标、收藏品/家具。主要操作通过点击场景中的物体或角色触发，避免长列表和满屏文字。
- 做**少量高质量运行时像素素材与轻量动画**：角色待机、篝火闪烁、灯光、奖励掉落、场景切换，保持统一像素比例、清晰轮廓和青绿/暖金调性；正式场景/精灵必须作为实际 app 资源或组件使用，**不能以概念图截图假装界面**。
- 适配小屏 Android、屏幕安全区和触控命中范围；保持低内存、不卡顿。若暂时缺少美术资产，优先完善一张主场景和一组人物/奖励图标，不要把资源精力平均分散到几十个场景。

### P0：完成训练后触发“可选择、能留痕”的随机冒险
- 设计并实现 **15–20 个可复用事件**，含短篇风味文案、像素事件插画/人物表情、2–3 个选择、各自的实际结果。事件类型覆盖探索、NPC 委托、发现物品、营地趣事、恢复日故事及小分支；不是仅更换任务标题或随机播报 XP。
- 事件需根据玩家的**真实训练或休息记录、既有委托结果、已去过地点、现有物品和 NPC 关系**解锁或改变权重。完成真实训练后进入一段简短“冒险战报”，提供事件与可点击选择，选择结果反映到存档。
- 用**预设事件数据 + 条件 + 加权/稳定随机种子**即可，不加 AI 调用或云服务。同一笔结算不可通过重启、反复进页面、编辑/删除训练来无限重抽或重复领取；未处理的事件能在重启后恢复。事件已经影响过奖励或世界状态时，删除训练按明确的规则撤销/冻结相关奖励，避免刷道具；已作出的叙事选择不意外丢失。
- 先做一个**完整、可重复游玩的故事闭环**：训练/休息 → 冒险战报 → 事件选择 → 世界状态变化 → 返回营地看到变化。动画短、可跳过，不挡住普通记录流程。

### P0：NPC、背包和可见奖励
- 营地先加入 **3 位有辨识度的 NPC**：老向导奥伦（探索/岩壁）、侦察员米拉（技巧/路线）、森林精灵苔苔（恢复/营地）。每位配置可重复的日常对话和约 5 个递进的短故事节点；拥有简单关系/信任进度、解锁条件，人物语言有明显差异。
- 增加小型**物品背包与收藏册**：先做约 10–15 种实物感强的收藏、装备外观、营地装饰或线索（如旧地图、指南针、徽章、灯笼、粉袋外观）。事件或真实任务可获得；玩家能查看来源、装备外观或摆放营地物品。
- 玩家在 UI 中应**看见**奖励带来的变化：NPC 新对话、背包新图标、角色换装、营地多出家具、地图揭示新标记。不要新增只存在于数字表里的货币和属性。
- 奖励结算需要幂等；补签和重复日志不得刷收藏品。装备外观为纯装饰，不暗示会提高现实攀岩能力。

### P1：个人攻关线路 → 冒险 Boss
- 允许玩家从已有线路图鉴中**主动指定一条现实线路为个人 Boss**，显示像素“山壁挑战牌”：难度、类型、相关照片/视频、目标和攻关故事。
- 攻关状态按照真实记录推进：路线预读 → 关键动作练习 → 连接动作片段 → 完攀。**“关键动作已解决”等无法自动验证的阶段要明确标记为玩家自评/手动进度**；最终完攀只能依据已记录的真实发送/线路数据判定。
- 失败尝试、复盘、休息可解锁非强度奖励或新情节，但不制造必须连续挑战高难度路线的压力。完成后可获取独特像素纪念品并留在图鉴。

### UI 与美术落地优先级
1. 一张营地游戏主场景、3 个 NPC、玩家角色待机动画、点击交互。
2. 训练结算的游戏战报 + 15–20 个带结果的事件 + 短反馈。
3. 物品/换装/营地装饰 + 存档持久化 + 场景可见变化。
4. 若剩余时间充足，再做个人线路 Boss 和局部地图探索。**不要牺牲前三项完整性。**

交互保持“**少文字、少滚动、多视觉、短动画、点选分支**”。中文文案简短自然，英文沿用现有 `src/i18n.ts` 机制；扩展文案集中维护。可将巨大 `App.tsx` 适度拆出营地/事件/背包组件，但不进行无关大重构。

### 最小验证（严格控制）
- 只执行必要的 `npm run typecheck`；环境允许时简单 Android 启动或复用已有 APK 工作流，**不要因 UI 改动反复跑耗时 12–19 分钟的完整 APK 构建**。
- 简单手动走通一条关键路径：真实训练或休息 → 事件选择 → 背包/NPC/营地变化 → 重启后仍存在；检查奖励不重复，旧存档仍可加载。
- 不扩展大型单元测试/E2E/CI，不写长篇测试报告；遇到必要阻断问题才修复。

### 完成标准 / 交付
- 打开 App 首屏是有生命力、可点击的**像素探险营地**，而不是一屏训练报表。
- 完成一条现实训练或恢复日志后，玩家能遇到有选择结果的故事事件，获得可见的收藏/装扮/关系变化，后续 NPC 对话或营地场景随之改变。
- 保持既有任务、真实记录、游戏数值、媒体引用和旧存档可靠；本轮不做 iOS、账号、云端、复杂经济系统或回合制战斗。
- **直接提交实际代码到 GitHub**；最终简短报告实现功能、commit SHA、未验证项目。不要只提交 goal 或说明文档。

**开始实现：优先把“一个精彩的完整游戏循环”做透，不要追求系统数量。**
