# RockClimbingHero · 新阶段开发目标

## Phase：先做成自己想玩的攀岩游戏

> **最高优先级：美术、UX/UI、动效、声音，以及它们共同构成的游戏体验。**
>
> 用户的直接反馈：「我不想玩现在这个 App。记录攀岩的话，我用备忘录就可以。」
>
> 下一阶段必须回答：**同样记录一次攀岩，为什么我会主动打开这个游戏，并期待再次回来？**
>
> 本文取代上一轮 goal.md 的优先级。随机委托、属性成长、线路图鉴不再是本轮首要交付。不能继续把视觉和声音放到“功能完成后再打磨”。本轮目标是实现可运行的高品质体验，不是只提交设计文档。

## 1. 产品目标与边界

- 让一次真实攀岩留下有情绪、有记忆点、可回看的游戏体验；记录依然要比普通表单轻松。
- 沿用 ASCENT 的山野探险像素 RPG 身份，以营地、岩壁、探索者和旅程构成统一世界。借鉴 WalkScape 等产品的完成度与整体感，不复制其资产、界面或经济系统。
- Android only；简体中文优先，保留英文切换；离线可用。沿用 React Native + Expo + TypeScript + SQLite，允许为实际呈现需要加入适量依赖。
- 保留现有用户档案、训练记录、XP、自评、语言设置和离线存档。不得清空数据，不为视觉改造重写无关业务系统。
- 本轮只实现下面定义的完整体验片段；旧功能入口继续可用，但不要求所有旧页面同时重做。

## 2. P0：先确立美术方向，用真实界面验证

先审视当前营地、角色、地图、记录页面与现有资产，指出导致“不想玩”的具体问题。不要只改配色、圆角或添加更多卡片。

在同一像素探险世界内制作 2–3 个轻量视觉候选：例如暖色篝火营地、清晨岩谷、夜色远征。每个候选至少展示真实手机比例下的营地主界面，包含角色、场景、中文文字与主要操作，不能只给情绪板。

- 用简短对比说明各方案的气氛、信息可读性和制作成本；选择一个最适合现有产品的方案继续实现，不把等待确认设为默认阻塞。
- 明确场景、角色、道具、图标、面板、字体、色板、光照与动画的共同规则。已有 ART_DIRECTION.md 作为基础，必要时同步修订冲突内容。
- 营地必须有明确视觉焦点、前中后景层次和可信的角色比例。角色、背景与 UI 不能像不同素材包拼接。
- 像素资产采用一致的像素密度和缩放规则，避免模糊放大、混用粗细或用 emoji 代替正式游戏资产。
- 中文正文优先清晰易读的字体；像素风可以用于短标题和数字，不以装饰牺牲阅读。
- 美术必须成为可运行的资产与界面。静态概念图不能充当交互页面；不得用整张 UI 图片覆盖真实控件。
- 使用原创或明确允许使用的素材；新增素材记录来源与许可，不直接搬运参考游戏资产。

## 3. P0：做通并打磨一段完整体验

**打开营地 → 开始记录攀岩 → 保存本次经历 → 看到有分量的完成反馈 → 回到留下变化的营地。**

### A. 打开就想停留的营地

- 首屏先让玩家感受到世界、角色与当前旅程，再传达必要信息。避免把任务、属性、统计全部堆成仪表盘。
- “记录攀岩”是清晰的主要操作。图标有易懂标签，点击区域可靠，不要求玩家猜测场景里哪些装饰能点。
- 为场景加入少量一致的环境生命感，如篝火、光影、旗帜或角色待机。动画服务于氛围，不让整个画面持续争抢注意力。
- 展示最近一次攀岩留下的具体痕迹，并能进入回看；不能每次打开都像同一张没有变化的壁纸。

### B. 攀岩后的轻松记录

- 检查当前记录流程的步骤、重复输入、术语、键盘遮挡与返回行为；删减无必要的阻力。
- 只要求保存现有数据模型真正需要的信息，合理提供默认值；心情、感想、照片等作为可选内容，不阻塞保存。
- 不强迫先接任务、完成自评或上传媒体才能记录。已有训练与疼痛相关保护不得被视觉改造绕开。
- 页面有清楚的层级、即时选中反馈与明确保存状态。防止连点造成重复记录，出错时保留输入并允许重试。
- 以现有记录能力为基础，不借机引入完整线路系统、相册原生模块或复杂训练计划。

### C. 接住完攀后的成就感

- 保存成功后呈现短而有节奏的完成反馈：本次真实记录的摘要、角色或场景反应、已有奖励的清晰来源，以及可跳过的动画。
- 声音、动效、触感形成一个完整节奏；不能只弹出普通提示框或机械堆叠数字。
- 如果展示 XP 或成长，复用现有规则并与实际保存结果一致。不得为播放奖励动画伪造属性提升或重复发奖。
- 完成后提供清楚的返回营地与查看本次记录入口，不让用户陷入多层领奖弹窗。

### D. 营地中看得见的回忆

- 完成记录后，营地里出现可持续回看的轻量变化，例如新增一枚旅程纪念或一页日志。选择一种做到完整，不同时开发多套收集系统。
- 痕迹与真实记录关联，重启后仍存在；修改或删除记录时保持一致。回看能看到这次攀岩，而不只是一个总数。
- 下一次打开能辨认上次发生了什么，同时保有清晰的下一步入口；不通过强制签到、休息惩罚或体能加码制造回来理由。

## 4. P0：声音、触感和动效必须实际落地

- 实现一条适合营地的轻量环境音，以及主要确认、记录保存成功和完成反馈等关键音效。声音要与山野像素世界一致，避免每点一次都响。
- 提供清晰的静音控制并持久保存；尊重 Android 的音频设置。切后台停止或暂停播放，回到前台不叠加音轨，不妨碍用户自己的音乐。
- 适量使用触感强化重要动作，设备不支持时正常运行；避免与声音一起高频轰炸。
- 页面转场、按压、进度变化与完成动画具有统一节奏。反馈立即响应，较长动画可以跳过，不阻塞下一步操作。
- 避免闪烁与强烈连续运动，支持减少动效；不依赖声音或颜色单独表达成功、错误与状态。
- 所有音频实际随离线应用可用；在资产清单记录来源、许可和用途。没有声音文件时不得用空实现宣称完成。

## 5. 本轮明确延期的工作

- 扩充每日／每周随机委托、任务故事池、经济系统与细粒度属性成长。
- 完整线路图鉴、多媒体持久授权、社交、公会、排行榜、商城和账号同步。
- 更多地图区域、角色职业、大量皮肤与剧情内容。
- 不直接改善上述体验片段的架构重构或大型测试工程。

已有能力保持可用。以后是否推进这些工作，以核心体验的实际效果决定；不得用新增功能数量代替体验质量。

## 6. 实施顺序

1. 审视当前运行界面，记录主要问题；制作轻量候选并选定视觉方向。
2. 建立本次需要的资产、字体和 UI 规范，完成营地主界面的真实实现。
3. 打磨记录流程，接通真实存储、完成反馈与营地回忆。
4. 加入声音、触感、转场与环境动画，并检查它们组合后的节奏。
5. 在 Android 上完成整段体验，修复可读性、触控、键盘、性能与声音生命周期问题；形成可安装版本供体验。

每一步都围绕同一段体验推进，不先做一个覆盖所有页面的庞大组件库。

## 7. 验收标准

### 体验验收：需要真实体验者判断

- 用户看到实际营地后，愿意打开和探索，能说出吸引自己的具体画面或细节。
- 新用户无需解释就能找到记录入口并保存一次攀岩，不需要猜图标含义。
- 完成反馈能呼应这次真实攀岩；用户愿意看完，且不会被强制拖住。
- 回到营地、关闭重开后，用户能找到本次攀岩留下的回忆。
- 用户愿意用它替代一次备忘录记录，并能说出具体原因。

**开发者不得自行宣布“用户已经喜欢”。交付可体验版本后，以上主观标准由用户反馈确认；不通过时优先修正体验，不继续堆新系统。**

### 基础质量：实现时必须检查

- 小屏 Android 上中文可读，主要触控目标至少约 48dp；键盘不遮住当前输入和必要操作，系统返回行为合理。
- 主路径没有占位图、emoji 临时代图、无反馈按钮或空音效实现；离线也能完整体验。
- 减少动效、静音、后台切换后行为正确，音轨不重复播放。
- 记录仅保存一次，已有奖励不重复发放；新旧记录与语言设置重启后仍正确。
- 不把游戏属性当成实际攀岩能力测量，不鼓励疼痛状态继续加量训练。

## 8. 验证与交付

- 文档更新本身不要求运行应用测试。实施代码时运行 `npm run typecheck`，对改动涉及的数据与奖励路径运行现有相关检查。
- 视觉与声音不能靠类型检查证明：必须在 Android 真机或模拟器走通上述流程，提供实际运行截图，以及能展示动效和声音的短录屏；无法验证的项目明确列出。
- 交付可安装 APK 或成功构建的下载地址。没有成功构建或设备验证时如实说明，不把设计稿、静态网页或演示视频当作 Android 成品。
- 提交实际代码、资产及必要的来源说明到 GitHub，报告 commit SHA、运行证据、已完成内容与剩余问题。

**本轮成功标准：把一个“备忘录也能替代”的攀岩记录工具，做成一段用户愿意打开、体验和回看的游戏。先让这一段值得玩，再扩大游戏。**
